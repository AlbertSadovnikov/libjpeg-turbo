# MJPEG to NV12: first baseline

[Manual BMI follow-up](../bmi-intrinsics/README.md) maps the compiler's emitted
instructions to source and tests BZHI/BEXTR plus a C sign-extension rewrite.
No general replacement for compiler-selected BMI2 is promoted: BEXTR regresses,
BZHI is marginal/workload-dependent, and the C rewrite loses in sequence fast
IDCT despite a better single-frame result.

Latest: [BMI2 on the current threshold-plus-pair loop](../bmi-current/README.md)
reduces full-sequence accurate NV12 time 2.13% (4.4040 to 4.3102 ms) and
fast-IDCT NV12 time 1.22% in a matched-archive comparison. BMI1/LZCNT and the
combined feature tier are not better than BMI2 alone.

Follow-up: [stb-inspired entropy benchmarks](../stb-entropy/README.md). Compact
LUT entries regressed; pre-shifted long-code thresholds added a small confirmed
gain over pair10. A separate actual-stb native-plane NV12 reference was slower.

[Zenjpeg-inspired follow-up](../zenjpeg-ideas/README.md): MSB alignment, adaptive
refill, clean-prefix fallback and two DC-only metadata implementations did not
establish a convincing full-NV12 gain over threshold-pair10.

Error visualizations and detailed batch-timed per-MCU stage measurements are
generated by `render_delta.py` and `stages.py`. The latest reports live in
`error-delta/` and `stages/`; see [the stage report](stages/README.md).

Measured 2026-10-31 on Ryzen 9 3900X, GCC 13.3 Release, embedded 1920x1080
4:2:2 webcam JPEG. Source: `benchmarks/nv12_bench.cc`. Production codec sources
remain unchanged; the pair10 libraries are the previously validated isolated
scalar-bulk + branchless two-AC-symbol prototype.

## Output contract

- Even image dimensions, 8-bit YCbCr 4:2:2 or 4:2:0 JPEG.
- NV12: full-size Y, followed logically by half-height interleaved Cb/Cr.
- Preserve JPEG **full-range** samples; no RGB round trip, limited-range
  conversion, or color-matrix conversion. NV12 storage alone does not specify
  range, matrix or chroma siting. Encoder configuration/metadata must agree.
- For 4:2:2, vertically average adjacent reconstructed chroma rows using
  `(a+b+1)/2`. For 4:2:0, interleave the native chroma directly. This is an
  explicit box-filter choice, not a claim of every encoder's preferred siting.
- Reuse the decompressor and scratch buffers. Accept caller-owned,
  CPU-accessible Y and UV pointers with independent strides. This supports
  pitched staging buffers, not writes directly into unmapped GPU memory.
- Accurate integer IDCT is the default. Fast IDCT is a separate quality option.

The planar reference uses `tj3DecompressToYUVPlanes8`, writing Y straight into
the final destination, followed by chroma filtering/interleaving. The raw-strip
path uses `jpeg_read_raw_data`: write Y directly where block padding permits,
retain only eight rows per chroma plane, and immediately filter/interleave
into the destination UV plane. Edge widths/bottom strips use guarded scratch
rows. SIMD packing uses runtime-dispatched AVX2 with a portable C fallback;
there is no whole-program AVX2 requirement. The portable C path may also be
auto-vectorized by the compiler.

## Measured results

Median of three per-run Google Benchmark CPU means, 0.2 s minimum measurement
and 0.03 s warmup per case, variant order rotated between rounds, CPU 0. Frame
data is compiled into every executable; no file loading is timed. Buffers and
decoder objects are reused. Values below are ms per frame:

| Path | Original codec | Scalar bulk | Pair10 |
|---|---:|---:|---:|
| BGR reference, accurate | 6.0697 | 5.9292 | 5.4988 |
| NV12 accurate, planar + AVX2 pack | 4.9997 | 4.8807 | **4.4079** |
| NV12 accurate, raw strips + portable pack | 4.9936 | 4.8893 | 4.4242 |
| NV12 accurate, raw strips + AVX2 pack | 4.9751 | 4.8865 | 4.4352 |
| NV12 fast IDCT, planar + AVX2 pack | 4.4834 | 4.4795 | 3.9923 |
| NV12 fast IDCT, raw strips + portable pack | 4.4830 | 4.4718 | 3.9928 |
| NV12 fast IDCT, raw strips + AVX2 pack | 4.4677 | 4.4600 | **3.9750** |

Accurate NV12 with pair10 is about **227 frames/s on one CPU core** for this
hot fixture; the separate fast-IDCT option is about 252 frames/s. These are
decode/CPU-output numbers, not GPU-upload or encode throughput. Accurate
pair10 NV12 takes about 11.4% less time than the fastest original-codec NV12
path in this run. No consistent strip-versus-planar speed win has been
established: the small differences depend on the variant. Strips reduce
intermediate storage even when they do not reduce time.

Packing prepared chroma alone takes about 0.031 ms with AVX2 and 0.034 ms with
portable C, a small portion of the roughly 4.4 ms accurate decode. Full paths
are decisive; stages have different cache behavior and are not additive.
CPU frequency was not fixed; these are one-scene measurements, not a guarantee
across cameras, CPUs or cold-frame sequences. `summary.json` retains all nine
cases, per-round records and the aggregation method. Per-run JSON/log files
remain local.

## Fast-IDCT differences

Compared with the accurate IDCT's NV12 output, on the embedded frame:

| Plane | Maximum absolute difference | Mean absolute difference | Samples changed | PSNR |
|---|---:|---:|---:|---:|
| Y | 5 | 0.509260 | 49.894% | 50.881 dB |
| Interleaved UV | 2 | 0.481573 | 48.157% | 51.304 dB |

Sample scale is 0..255. These measure the difference between two reconstruction
methods, not error against an uncompressed camera original or guaranteed visual
quality. Fast IDCT remains opt-in pending the user's quality decision.

## Validation

Before timing, the executable requires exact equality of planar-reference and
raw-strip NV12 outputs, including portable/AVX2 packing, for both IDCT modes.
It also checks independent unaligned Y/UV strides and verifies every padding
byte remains unchanged. `validate.py` generates seven additional fixtures and
runs these checks against original and pair10 libraries: 14 combinations.
Fixtures cover non-DCT-aligned widths/heights, AVX2 tails, 4:2:2/4:2:0, two-row
images, restart markers, and progressive input. `validation.json` records them.
Both existing MJPEG and new NV12 benchmark smoke tests pass.

## Reproduce

```sh
cmake -S . -B /tmp/mjpeg-google-bench -DCMAKE_BUILD_TYPE=Release \
  -DENABLE_SHARED=OFF -DWITH_BENCHMARKS=ON
cmake --build /tmp/mjpeg-google-bench --target nv12-bench -j 6
taskset -c 0 /tmp/mjpeg-google-bench/benchmarks/nv12-bench \
  --benchmark_min_time=0.2s --benchmark_repetitions=3
ctest --test-dir /tmp/mjpeg-google-bench -R '^(nv12|mjpeg)-bench-smoke$' \
  --output-on-failure
```

For three-library comparisons, `python3 test/webcam/nv12/run.py`; for generated
fixtures, `python3 test/webcam/nv12/validate.py`. These scripts require the
retained original/scalar/pair10 libraries and Google Benchmark source/build
under `/tmp`, as explicitly listed in `run.py`. Neither script installs CUDA,
alters production codec code, or measures a GPU pipeline.

## Next work

The user targets GPU upload and H.264/H.265 encoders. The local GPU is an
RTX 3090 Ti with driver/encoder libraries available. A CUDA toolkit/nvJPEG
library was not found in the standard locations inspected. Do not infer a
GPU decode result or speedup from these CPU tests. Next, establish the actual
upload/encoder API and its range/siting/stride contract; measure CPU decode,
upload and encoding together, and evaluate GPU-resident JPEG alternatives.
For CPU decoding, entropy/IDCT work matters much more than further tuning the
already-small chroma-packing stage.
